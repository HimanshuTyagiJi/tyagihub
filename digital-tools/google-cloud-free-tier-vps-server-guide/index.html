Google Cloud Always Free Server: How to Host Python Bots, Cron Jobs & Webhooks for ₹0 Forever (2026 Guide)

By Himanshu Tyagi
• November 24, 2026 • Category: Digital Tools
Share this guide: 🐦 X (Twitter) 💼 LinkedIn 💬 WhatsApp

If you build custom Telegram bots, run automated web scrapers, schedule nightly database backups, or listen for Stripe and Razorpay payment webhooks, you quickly hit a frustrating barrier: your local computer cannot stay on 24 hours a day, 7 days a week.

The standard developer advice is to spin up a basic cloud server (VPS) on DigitalOcean, Linode, or AWS Lightsail. However, the cheapest entry-level instances on these platforms now cost $6.00 to $8.00 per month. When you add foreign transaction conversion fees and 18% Indian GST, you are paying between ₹6,500 and ₹9,500 every single year simply to keep a tiny 50-line Python automation script running in the background.

What most independent developers, freelancers, and solopreneurs do not realize is that Google Cloud Platform (GCP) provides a 100% free virtual server forever through its official Always Free tier. Unlike the temporary 90-day trial credits offered by competitors, Google Cloud’s e2-micro compute tier does not expire as long as you stay within the specified regional hardware limits.

In this exhaustive, verified blueprint, I will guide you step-by-step through setting up an e2-micro Ubuntu server on Google Cloud, configuring the critical 2GB swap memory to prevent Out-Of-Memory (OOM) crashes, deploying self-healing 24/7 background tasks using systemd, and configuring an automated ₹1 budget alert so you never receive an unexpected bill.

💰 The Financial Value of Google Cloud's Always Free Tier

Over a 3-year period, hosting an entry-level virtual server on DigitalOcean or AWS costs roughly ₹21,000 to ₹28,000. By provisioning Google Cloud’s official Always Free e2-micro instance, your infrastructure expense is ₹0.00 forever. Pair this with our free GitHub Pages custom domain hosting and you have a complete zero-cost production cloud stack.

2. Step-by-Step: Provisioning the Free e2-micro VM

Follow these exact configuration steps in the Google Cloud Console to ensure your instance falls 100% under the Always Free discount:

  1. Navigate to the Google Cloud Console and sign in with your Google account.
  2. Create a new project (e.g., tyagihub-cloud-automation).
  3. Open the navigation menu and click Compute Engine > VM instances. (Click "Enable API" if prompted and wait 60 seconds).
  4. Click the blue Create Instance button at the top.

Configuring the Instance Parameters:

  • Name: free-automation-node
  • Region: Select us-central1 (Iowa) • Zone: us-central1-a (or b/c/f).
  • Series: Select E2.
  • Machine type: Choose e2-micro (2 vCPU, 1 GB memory) from the dropdown list.
⚠️ The Boot Disk Trap (Most Common Mistake)

By default, Google Cloud configures a Debian image on a 10 GB "Balanced Persistent Disk". Balanced Disks are NOT free! You must click Change under Boot Disk, select Ubuntu (Ubuntu 24.04 LTS x86/64), change the Boot disk type to Standard Persistent Disk, and set the size to 30 GB.

  • Firewall: Check both Allow HTTP traffic and Allow HTTPS traffic if you plan to run webhooks.
  • Click Create at the bottom of the page. Within 30 seconds, your virtual machine will spin up with a green checkmark.

4. The Critical Memory Fix: Configuring 2GB Linux Swap Space

The e2-micro instance provides exactly 1 GB of physical RAM. While this is sufficient for Linux itself, running modern Python scripts, installing NPM packages, or compiling C-extensions can easily spike memory to 1.1 GB.

Without swap space, the Linux kernel triggers the Out-Of-Memory (OOM) Killer, abruptly killing your background bots and terminating your SSH session. Because Google gives us a generous 30 GB boot disk, we can allocate a 2 GB swapfile on the SSD storage, effectively giving our server 3 GB of virtual memory:

💻 BASH
# 1. Allocate a 2GB file on the root filesystem
sudo fallocate -l 2G /swapfile

# 2. Restrict permissions so only root can read it
sudo chmod 600 /swapfile

# 3. Mark the file as Linux swap area
sudo mkswap /swapfile

# 4. Enable the swap space immediately
sudo swapon /swapfile

# 5. Make swap permanent across system reboots
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 6. Optimize swappiness (prefer physical RAM, use swap only as a safety net)
sudo sysctl vm.swappiness=10
echo 'vm.swappiness=10' | sudo tee -a /etc/sysctl.conf

Verify that your virtual memory is active by running free -h. You will see Swap: 2.0Gi ready and operational. Your server will now run heavy scripts smoothly without random crashes.

5. Running 24/7 Bots & Scripts with Systemd (Self-Healing Daemons)

If you launch a script by simply typing python3 bot.py, it will stop the moment you close your browser or your internet disconnects. While tools like screen or tmux keep terminal sessions alive, they cannot recover if the server reboots for Google maintenance.

The industry-standard solution on Linux is systemd. Systemd runs your application as an official background daemon, starts it automatically when the server boots, and restarts it automatically if it ever crashes.

For example, let's configure our Personal Telegram Cloud Automation Bot to run 24/7 forever:

Step 1: Create a systemd service file:

💻 BASH
sudo nano /etc/systemd/system/telegram-bot.service

Step 2: Paste the following service configuration:

💻 INI
[Unit]
Description=TyagiHub 24/7 Telegram Cloud Bot Service
After=network.target

[Service]
Type=simple
User=himanshu
WorkingDirectory=/home/himanshu/telegram-bot
ExecStart=/usr/bin/python3 /home/himanshu/telegram-bot/bot.py
Restart=always
RestartSec=5
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target

Step 3: Enable and start your background service:

💻 BASH
# Reload systemd to recognize the new service
sudo systemctl daemon-reload

# Enable service to launch automatically on server boot
sudo systemctl enable telegram-bot

# Start the service right now
sudo systemctl start telegram-bot

# Check the live status and execution logs
sudo systemctl status telegram-bot

With Restart=always configured, even if your script encounters an unexpected API timeout or network glitch, Linux will wait 5 seconds and automatically reboot it without any manual intervention.

6. The Zero-Cost Guardrail: Setting a ₹1.00 Budget Alert

The biggest fear developers have with cloud providers is receiving a shocking bill at the end of the month due to a forgotten setting or unexpected outbound traffic. We completely neutralize this risk using Google Cloud's native billing alerts:

  1. In the Google Cloud navigation menu, go to Billing > Budgets & alerts.
  2. Click Create Budget.
  3. Set the Budget Name to Zero-Cost Safety Shield.
  4. Under "Budget type", select Specified amount and enter ₹1.00 (or $1.00 USD).
  5. Under "Set alert threshold rules", add triggers at 50%, 90%, and 100%.
  6. Check Email alerts to billing account administrators.
  7. Click Finish.

If your account ever consumes even ₹0.50 ($0.01) worth of non-free resources, Google Cloud will immediately send an alert straight to your primary email address so you can inspect and stop it before any significant charge occurs.

8. Frequently Asked Questions (FAQ)

Does Google Cloud require a credit card for Always Free tier?

Yes. Google requires credit card or international debit card verification to prevent fraudulent bot-net accounts. They make a temporary refundable authorization charge of ₹2.00 (or $1.00) that is reversed immediately. As long as you stay within the e2-micro US regional limits outlined in this guide, your card will never be billed.

Will my server stop working when the $300 90-day free trial credit expires?

No. Google Cloud explicitly separates the "90-Day Free Trial" from the "Always Free Products". Even after your $300 trial credits expire, the e2-micro instance (in US regions) continues running indefinitely at zero cost under the permanent Always Free quota.

What happens if I stop and restart the virtual machine?

By default, Google assigns an ephemeral external IP address. If you shut down the machine and power it back on, the public IP address may change. For Telegram bots or background scrapers making outbound requests, this does not matter at all. If you are pointing a custom domain to it, use a free dynamic DNS client or keep the VM running continuously.
